支援的介面¶

Setuptools 是一個複雜的程式庫，擁有許多介面面和挑戰。除了作為打包建置後端的主要用途外，Setuptools 在歷史上也擔任過獨立的建置工具、安裝工具、上傳工具、中繼資料提供者等角色。此外，由於它以 Python 程式庫的形式實作，其全部功能也間接地以程式庫的形式暴露出來。

除了作為程式庫運作之外，由於新版本的 Setuptools 常被用來建置較舊的（有時是數十年前的）軟體包，因此它承擔著很高的穩定性負擔。

為了能夠對專案進行合理的變更，下游開發者和使用者應避免依賴程式庫的內部實作細節，而應僅依賴受支援的介面：

  • 第一層：現代 PyPA 打包標準 (PEP 517, PEP 660) 所需的 API，以及用於自訂建置行為或建立外掛程式的已文件化 API（Extending or Customizing Setuptools、關鍵字）：

    這些 API 預期將極為穩定，並且在向後不相容的變更或移除之前，會有棄用通知和緩衝期。

    請注意，功能測試和整合測試 捕捉了程式庫和系統預期如何為外部使用者運作的特定行為和期望；而*程式碼註解和文件字串*（包括測試中的）可能提供特定保護，以限制下游使用者可依賴的行為變更。

  • 第二層：已文件化的 distutils API：

    setuptools 致力於尊重 distutils 所提供的介面，並將與 pypa/distutils 倉儲協調，以便發出適當的棄用通知。

    原則上，這些在 API Reference 中有文件說明。但請注意，當有合適的替代方案可用或建議使用時，現有的 distutils API 將被視為已棄用，不應再使用（請參見 PEP 632#migration-advice 和 Porting from Distutils）。

依賴其他行為是有風險的，且可能在未來遭受破壞。如果某個專案希望考慮使用上述未涵蓋的介面，請考慮在依賴它們之前，先請求將這些介面加入（例如透過提交實作該變更及相關回歸測試的拉取請求）。

請查閱Guides on backward compatibility & deprecated practice以了解更多關於已棄用和不受支援行為的資訊。

支援政策例外情況¶

明確記錄或宣告為已棄用的行為和介面，或發出棄用警告的項目，將在公告的棄用期限內繼續獲得支援。

然而，在某些情況下，Setuptools 維護者保留加快棄用週期和縮短棄用期限的權利：

  1. 當特定程式碼路徑中發現安全漏洞，且重新設計現有 API 不可行時。

  2. 當 Python 打包生態系統中的標準從外部驅動程式碼庫中的非向後相容變更時。

  3. 當行為變更由第三方依賴以及在 pypa/setuptools 倉儲之外維護的程式碼外部驅動時。

請注意，這些是例外情況，專案在訴諸於非預定移除之前，將仔細嘗試尋找替代方案。

重要

在 setuptools 的上下文中，引入 warnings`（包括棄用警告）本身 *並不* 被視為重大變更。相反地，它被視為一種向後相容的*溝通行為*，預示著即將到來的重大變更。這是因為包含警告的程式碼通常不會失敗，並且可以成功完成執行，除非使用者明確選擇將這些警告轉換為錯誤（例如，透過 Python 的 :external+python:ref:-W 選項或 PYTHONWARNINGS 環境變數 <using-on-warnings>`）。

當棄用期限未定義時該怎麼辦？¶

在某些情況下，很難界定 Setuptools 需要多長時間來移除某些功能、行為或 API。例如，評估某個功能在生態系統中的使用廣泛程度可能相當複雜。

因此，Setuptools 可能會在沒有明確到期日的情況下開始發出棄用警告。這是因為我們希望盡快通知使用者即將到來的重大變更，以便他們可以開始制定遷移計畫。

這並不意味著使用者應將此棄用視為低優先級，或將缺乏到期日解讀為重大變更永遠不會發生的信號。

建議的做法是，使用者一旦發現自己受到 Setuptools 棄用影響，就應盡快制定遷移計畫。

當棄用警告已經在沒有明確到期日的情況下發出很長一段時間時，Setuptools 可能會引入相對較短的棄用期限（例如 6 個月）。

如何掌握即將到來的棄用資訊？¶

最好在專案中使用覆蓋率較佳的自動化測試軟體包，並留意日誌。你也可以透過將標準輸出/錯誤串流轉發到日誌檔案，並使用啟發式方法來識別棄用（例如搜尋 deprecation 或 deprecated 字詞）來自動化此過程。你可能需要提高輸出的詳細程度，因為某些工具預設會隱藏日誌訊息（例如透過 pip -vv install ...）。

此外，如果你維護的專案依賴於 Setuptools，你可以實作一個 CI 工作流程，利用 Python 警告過濾器 來提高警告的可見度。

此工作流程例如可以包含 3 個疊代步驟，要求開發者確認棄用警告：

  1. 利用 Python 警告過濾器，在自動化測試期間將警告轉換為例外。

  2. 制定遷移計畫：

    • 最好將棄用事項像問題一樣追蹤，並應用專案管理技術來監控處理進度。

    • 判斷程式碼中哪些部分受到影響，並了解消除警告所需的變更。

  3. 修改你在 CI 中使用的警告過濾器，使其不會因為新識別的例外而失敗（例如，使用 default 動作搭配特定的類別或正規表達式來比對警告訊息）。這可以針對整個測試軟體包全域設定，也可以在逐項測試的基礎上局部設定。

像 pytest 這樣的測試工具提供了 CLI 和設定選項，以便於控制警告過濾器（請參見 How to capture warnings）。

請注意，有許多方式可以將此工作流程整合到你的 CI 中。例如，如果你有足夠的部署資源，並將棄用警告管理視為日常開發測試，你可以直接在主要 CI 迴圈中設定警告過濾器。另一方面，如果你有嚴格的時間表，無法承受 CI 工作偶爾因標記維護而失敗，你可以考慮排程一個與主要/關鍵任務工作流程分開的定期 CI 執行。

「支援」是什麼意思？¶

Setuptools 是一個非營利、由社群驅動的開源專案，因此「支援」一詞是以盡力而為且範圍有限的方式使用。例如，並非總能快速提供錯誤修正。

我們感謝社群的耐心，並鼓勵受到錯誤影響的使用者以提交 PR 的形式貢獻修正，以加快處理速度。

當我們說「某個功能受到支援」時，意思是我們會盡最大努力確保該功能按文件說明的正常運作。但請注意，與任何系統一樣，仍可能發生非預期的損壞。我們感謝社群的理解與體貼的回饋。

棄用期限結束後該怎麼辦？¶

如果你的開發資源有限，無法在 Setuptools 移除已棄用功能之前制定遷移計畫，你仍然可以限制所安裝的 Setuptools 版本。這通常包括修改 pyproject.toml 中的 [build-system] requires，和/或透過 PIP_CONSTRAINT 環境變數指定 pip :external+pip:ref:`約束檔案 <Constraints Files>`（或傳遞 --build-constraint to uv）。但請避免在沒有必要的情況下預先加入版本約束（你可以在 https://iscinumpy.dev/post/bound-version-constraints/ 閱讀更多相關資訊）。

關於「公開名稱」的說明¶

Python 開發者可能習慣於私有成員以 ``_``（底線）字元為前綴的慣例，並且任何未被此標記的成員即為公開。但由於 Setuptools 的歷史和遺留問題，情況並非一定如此 [1]。

在此專案中，「公開介面」被定義為明確文件化供第三方使用的介面。

在存取 setuptools 軟體包中的成員時，請確保該成員已被文件化為外部用途。另請注意，從不同模組/子模組匯入的名稱被視為內部實作細節，除非它們被明確列在 __all__ 中。它們在執行 import 的模組命名空間中可被存取，這只是 Python 運作方式的副作用。

[1]

雖然以 _ 為前綴的名稱始終被視為私有，但沒有此前綴並不一定表示該成員為公開。
